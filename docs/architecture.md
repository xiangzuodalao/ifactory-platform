# 平台架构

## 当前阶段

`ifactory-platform` 是四个独立仓库的组合与治理入口：

| 组件 | 当前职责 |
|---|---|
| CMMS | 资产、工单、维护计划、人员与备件 |
| ThingsBoard | 设备、遥测、告警与规则链 |
| PDM Algorithm | 数据检查、模型训练、预测与模型产物 |
| `digital-mcp` | 将平台 HTTP API 暴露为受控 MCP 工具；当前只适配 PDM |

本阶段仅整理目录、Git、Codex、Skills 和现有 MCP，不实现 CMMS、ThingsBoard 与 PDM 之间的新业务链路，也不提供生产部署。

## Codex 扩展模型

平台不维护独立 `agent/` 目录，也不依赖 OnCall-Agent。Codex 直接从仓库根目录工作：

```text
用户
  │
  ▼
Codex ──读取──> AGENTS.md
  │
  ├──执行──> Skills（任务流程、安全门和结果约束）
  │
  └──调用──> digital-platform MCP
                   │
                   └──HTTP──> PDM API（当前）
```

- `AGENTS.md` 保存跨组件长期规则。
- Skill 描述一个边界清晰、可复用的任务流程，不承载业务服务。
- MCP 负责实时读取和受控操作，不承担自主规划。
- Codex 负责理解意图、调用 Skill/MCP、展示结果以及在写操作前取得确认。

模型训练属于高风险写操作：必须先预检，在后续对话轮获得明确确认后执行一次；提交结果不确定时只能查询状态，不得自动重试。

## 服务边界

每个组件拥有自己的数据库、配置和内部领域模型。禁止：

- CMMS、ThingsBoard、PDM 或 MCP 直接读写其他组件数据库；
- 通过复制数据库表或共享 ORM 模型耦合组件；
- 让 MCP 绕过业务 API 修改持久化状态；
- 将训练数据、模型产物、连接串或凭据提交到平台仓。

未来跨组件集成只能通过 `contracts/` 中有版本的 HTTP API 或事件契约。设备与资产映射、关联 ID、幂等键和追踪 ID 必须在接口中显式传递。

## 仓库边界

总仓只锁定组件提交并维护组合层内容：

- Git submodule 指针；
- Codex 配置与项目 Skills；
- 平台契约、部署编排、文档和跨组件测试。

业务代码继续在对应组件仓库内提交。一次跨组件改动应先合入并推送组件提交，再更新总仓的 submodule 指针，确保任一平台提交都能完整复现。
